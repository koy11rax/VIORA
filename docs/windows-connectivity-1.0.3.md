# Windows 1.0.3: подключение и диагностика

Статус: сборка для проверки исправлений. Работоспособность реального Windows
туннеля после этих изменений пока не подтверждена.

## Изменения

- Адрес VPN-сервера разрешается до создания Windows TUN. Используется
  фиксированный HTTPS DNS с обычной проверкой сертификата. В режиме обычной
  сессии предусмотрен ограниченный по времени системный DNS, если HTTPS DNS
  недоступен. При постоянной защите такой переход запрещён.
- Замена адреса на IPv4 сохраняет имя TLS и исходные HTTP Host для WS/XHTTP.
- Отмена подключения прерывает поиск адреса сервера.
- Завершение локального канала больше не скрывает исходную ошибку службы.
- При отвязанном устройстве обновление подписки предлагает разрешить
  существующее устройство в боте; сохранённые серверы остаются доступны.
- Служба сохраняет только категории ошибок и счётчики в
  `Program Files\Viora\Engine\session-diagnostics.json`. Адреса серверов,
  назначения трафика, ссылки подписки, ключи и исходные строки журнала в отчёт
  не попадают. Отчёт заменяется после завершения следующей сессии.

## Подтверждённые наблюдения до установки

После разрешения существующего устройства в боте изолированные запросы через
WS TLS с выходом через физический Ethernet получили HTTP 204 (432 мс), а
HTTPS DNS — HTTP 200 с корректным ответом (417 мс). Эти запросы не создавали
TUN и не изменяли маршруты компьютера.

В Windows 1.0.0 при подключении, включённом пользователем, TUN и маршруты
создавались, но три HTTPS-запроса завершались по таймауту. Запрос DNS к
виртуальному резолверу также не получил ответа. HTTPS с заранее известным IP
и исходным TLS-именем завис на рукопожатии. MTU сетевого интерфейса был 1500;
forwarding и weak host на Ethernet были выключены. Поэтому ошибка браузера
сама по себе не доказывает проблему сертификата или только DNS.

Успешные изолированные запросы не являются проверкой полноценного туннеля,
Discord, DNS/IPv6 утечек или длительной работы. Настройки защиты и привязка
устройства в ходе диагностики не сбрасывались.

## Автоматические проверки

- Flutter: 178 успешных тестов, 5 пропущенных; анализатор без замечаний.
- Windows helper: 76 успешных проверок Go, 1 пропущенная; `go vet` без замечаний.
  Переменные `VIORA_TEST_CORE` и `VIORA_TEST_SERVICE` отключены: действующая
  служба и туннель в этих тестах не запускались.
- C++ IPC: 18 изолированных сценариев прошли (одна цель CTest).
- Linux helper: тестовый исполняемый файл скомпилирован для Linux; не запускался.
- MSI: проверены 30 хешей полезной нагрузки, выбор папки приложения, защищённые
  пути движка, автоматическая служба и сохранение защиты при обновлении.
- EXE: хеш вложенного MSI совпал с хешем проверенного пакета.

Тесты разрешения адреса используют подставные ответы и проверяют отмену,
таймауты, повреждённые и слишком большие ответы, отсутствие IPv4 и сохранение
имён TLS/Host. Тесты диагностики проверяют фиксированный словарь, ограничения
счётчиков, отсутствие секретов, параллельный доступ и дренирование слишком
длинных строк.

## Пересборка установщика r2

Ручная установка первой сборки завершилась ошибкой MSI 1920 после длительного
ожидания. Windows Installer откатил обновление к 1.0.0. Служба возвращала
собственный код `3` при отказе проверки каталога/файлов, а Windows ошибочно для
этого случая описывала его как системное отсутствие пути. Состояние файлов
именно в момент отказа старый журнал не сохранил; для установления причины
понадобился подробный журнал r2 (см. ниже).

В r2 все прежние проверки доверенного пути, reparse points и хешей сохранены.
Перед запуском службы helper проверяет установленные компоненты. Вместо
стандартного `StartServices` используется синхронное проверяемое действие
SYSTEM с фиксированным аргументом `--install-start`; оно не принимает VPN
конфигурацию и не запускает туннель. Проверка состояния службы имеет бюджет
15 секунд и одну попытку запуска. Время блокирующих вызовов SCM и самой
транзакции MSI контролирует Windows, поэтому весь установщик не объявляется
ограниченным 15 секундами. Ошибка вызывает штатный откат MSI.

Точные фиксированные причины отказа и числовые коды сохраняются в
`Program Files\Viora\Engine\installation-diagnostics.json`, когда защищённый
корень доступен. Собственные ошибки службы передаются как service-specific,
а не как случайные Win32-коды.

Установщик оставляет подробный локальный журнал в
`%LOCALAPPDATA%\Viora\installer-logs` и предлагает открыть его при ошибке.
Каталог/файл защищены DACL; точки перенаправления отклоняются. Принудительное
сбрасывание каждой строки журнала на диск выключено.

Проверки r2: Go 107 PASS, 1 SKIP, `go vet` PASS; 14 изолированных сценариев
проверки метаданных MSI; 4 проверки настоящих функций ACL/reparse без запуска
установщика; MSVC Release PASS; 30 хешей MSI и вложенный пакет EXE совпадают.
Установка r2 завершилась ошибкой `trust_failed / driverattrs`, что позволило
установить точную причину. Подключение VPN новой сборки ещё не проверено.

## Подтверждённое исправление r3

В builder использовалось условие `FileMajorPart > 0`. Оно ошибочно считало
официальный Wintun `0.14.1.0` файлом без версии. MSI видел более высокую версию
у установленного драйвера и запрещал установку нового компонента. Затем
удаление старого продукта удаляло прежний DLL; новый пакет его уже пропускал.
В журнале r2 есть все звенья: `higher versioned keyfile exists`, действие нового
компонента `Null`, удаление старого `wintun.dll` и отсутствие его копирования до
проверки helper. Драйвер восстанавливался только при откате.

Версии теперь читаются через `WindowsInstaller.Installer.FileVersion` и
сверяются для каждого файла пакета с его настоящими метаданными. В MSI r3
у Wintun записано `0.14.1.0`, исходный подписанный DLL и его SHA256 сохранены.
Регрессионные проверки включают настоящий драйвер с нулевой старшей версией
и файлы без ресурса версии (11 проверок прошли).

Дополнительно выполнен read-only расчёт плана MSI на ПК со старой 1.0.0, без
выполнения установки: для r2 `ComponentRequestState(C00002) = -1`, для r3 —
`3`, то есть исправленный пакет действительно планирует установку драйвера.

Измеренная транзакция r2 длилась около 183,52 с. Две проверки занятых файлов
заняли 78,680 и 78,148 с; helper выполнялся 0,069 с. Принудительное отключение
Restart Manager убрано, используется стандартное управление занятыми файлами
Windows. Старый закешированный пакет 1.0.0 по-прежнему может выполнить свою
долгую проверку во время первого обновления. Ускорение r3 в реальной установке
измерено после ручной установки пользователем: транзакция r3 заняла около
87 секунд, из которых около 78 секунд пришлись на проверку старого пакета.
Пользователь подтвердил успешную установку. Все 30 установленных файлов
совпали с комплектом по SHA-256, служба работала, её локальный отчёт содержал
`service_running`. Однако реальная передача трафика через VPN осталась
неисправной; успешная установка не считается исправлением сети.
